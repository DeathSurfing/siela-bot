# Siela admin dashboard

The dashboard is a self-hosted control panel for the bot. It shows bot health, connected servers, feature flags, music playback, scheduled voice events, game tables, economy, leaderboard, stock trading, server settings, user settings, audit history, and registered commands. The selected server stays in the URL and in browser storage.

## Set up the dashboard

`scripts/podman-init.sh` generates `DASHBOARD_PASSWORD` and `DASHBOARD_SESSION_SECRET` with the rest of the stack secrets and prints where the password is stored. Read it with:

```sh
grep DASHBOARD_PASSWORD deploy/podman/.env
```

To set your own values, export them before running the init script or edit `.env` afterwards. The password must have at least 12 characters and the session secret at least 32. To sign in with Discord only, remove `DASHBOARD_PASSWORD` from `.env` and set the four OAuth values. The dashboard exits at startup when the session secret is missing, when a password is too short, or when neither sign-in method is configured.

`MCP_TOKEN` is the same bearer token used by the bot control API. `CONTROL_API_URL` is the bot control service address. In the Podman stack, the default is `http://bot-control:3001`.

### Required environment

The dashboard reads these values from `deploy/podman/.env` through the compose `env_file`. Do not put them in `compose.yaml` or a command line.

| Variable | Required | Purpose |
| --- | --- | --- |
| `DASHBOARD_PASSWORD` | no | Password sign-in, 12+ characters. Omit it to disable password sign-in and require Discord. |
| `DASHBOARD_SESSION_SECRET` | yes | HMAC signing secret, 32+ characters. |
| `MCP_TOKEN` | yes | Same bearer token as the bot control API. |
| `CONTROL_API_URL` | yes | Control API address, `http://bot-control:3001` in the stack. |
| `DASHBOARD_PORT` | no | Host port. The container listener stays on 3000. Defaults to 3000; the current host uses 3002. |
| `DASHBOARD_BIND` | no | Host interface. Defaults to `0.0.0.0`; keep it there when Caddy runs on another host. |
| `DASHBOARD_HOST` | no | Container listener. Compose sets `0.0.0.0`. |
| `DASHBOARD_TRUST_PROXY` | behind a proxy | Set `true` when Caddy or nginx is in front, so client IP and HTTPS protocol are trusted. |
| `DASHBOARD_SECURE_COOKIES` | no | Set `true` only when every access is HTTPS. Keep `false` while the LAN HTTP URL is used; HTTPS requests get `Secure` automatically with `DASHBOARD_TRUST_PROXY=true`. |
| `DISCORD_CLIENT_ID` | for OAuth | Discord application ID. Already present for the bot. |
| `DISCORD_CLIENT_SECRET` | for OAuth | Discord application client secret. This is not the bot token. |
| `DASHBOARD_OAUTH_REDIRECT_URI` | for OAuth | Exact registered callback. |
| `DASHBOARD_OWNER_IDS` | for OAuth | Comma-separated Discord user IDs allowed to sign in. |

A complete host configuration with Discord-only sign-in. Add `DASHBOARD_PASSWORD=...` to keep the password fallback:

```sh
DASHBOARD_SESSION_SECRET=...
MCP_TOKEN=...
CONTROL_API_URL=http://bot-control:3001

DASHBOARD_HOST=0.0.0.0
DASHBOARD_PORT=3002
DASHBOARD_BIND=0.0.0.0
DASHBOARD_TRUST_PROXY=true
DASHBOARD_SECURE_COOKIES=false

DISCORD_CLIENT_ID=...
DISCORD_CLIENT_SECRET=...
DASHBOARD_OAUTH_REDIRECT_URI=https://dashboard.adityavikram.dev/auth/discord/callback
DASHBOARD_OWNER_IDS=...
```

Build and start the dashboard with the rest of the stack:

```sh
podman compose -p siela -f deploy/podman/compose.yaml up -d --build dashboard
```

The front end is plain ES modules. The TanStack Hotkeys bundle is generated by `bun run --cwd apps/dashboard build:client`; `build` and `dev` run it automatically. Run `build` before `start` in a source checkout.

### Host deployment

The compose service reads `deploy/podman/.env` through `env_file`, so the dashboard sign-in settings and session secret stay in that file. Do not put them in `compose.yaml`, a compose override, or a shell command. When set, the password must have at least 12 characters; the session secret must have at least 32. If you remove the password, the four OAuth values must be complete or the dashboard exits at startup.

The watchtower deploys the bot, TTS, router, and voice workers. It does not build or start the dashboard. After a stack update, build and start the dashboard explicitly from the repository root:

```sh
cd deploy/podman
podman-compose -p siela -f compose.yaml -f compose.voice.generated.yaml -f compose.watchtower.yaml build dashboard
podman-compose -p siela -f compose.yaml -f compose.voice.generated.yaml -f compose.watchtower.yaml up -d --no-deps dashboard
curl -fsS http://127.0.0.1:3002/healthz
```

The container listener stays on port `3000`. `DASHBOARD_PORT` is the host port in `.env`; on the current host the portfolio owns `3000`, so it is set to `3002` and the dashboard opens at `http://<host>:3002`. `DASHBOARD_BIND=0.0.0.0` publishes it on the LAN; use `127.0.0.1` when a local TLS proxy terminates the connection.

The dashboard container is `siela-dashboard`, has restart policy `unless-stopped`, and exposes `/healthz`. It is not in the watchtower deploy set, so a stack deploy leaves it running.

Put a TLS reverse proxy in front of any public-facing deployment. Set `DASHBOARD_TRUST_PROXY=true` so the client IP comes from the proxy and the sign-in limit applies per operator. Keep `DASHBOARD_SECURE_COOKIES=false` while the LAN HTTP URL is still used; with `DASHBOARD_TRUST_PROXY=true`, the dashboard adds `Secure` on HTTPS requests. Set it to `true` only when every request reaches the dashboard over HTTPS. Do not publish the dashboard port directly. The current host uses Caddy on `192.168.1.2` for `https://dashboard.adityavikram.dev` and forwards to `192.168.1.3:3002`; the dashboard binds `0.0.0.0` so the proxy can reach it. Do not expose the bot control API.

## Interface principles

The interface stays flat. Rules and spacing group content; nested cards do not. The topbar carries the navigation toggle below 700px and bot status. The page heading carries the view name. The rail header carries the server picker, with the selected server's Discord image and name, so scope is changed in the menu instead of a topbar dropdown; the picker is the only server switcher, and the rail has no Servers entry; an old `#/servers` link opens Overview. The desktop rail collapses to a 58px icon column from a chevron beside the picker and remembers that choice. Below 700px the persistent rail gives way to a hamburger button that opens the same navigation, picker, and labels as a left drawer. The Overview keeps one status line, three centered metrics, and two rule-separated columns. Features are compact rows, and their commands live in the Commands view instead of repeating on every row. Audit keeps the action source.

The Server settings view saves one section at a time. A save no longer re-renders the view, so unsaved edits in other sections survive. `Ctrl` or `Cmd` plus `S` saves every dirty section. A dot next to Save marks an unsaved section. User settings shows the signed-in Discord profile and a birthday form for the selected server. The profile chip in the rail is the only entry to User settings, from a mouse, keyboard, the collapsed rail, or the mobile drawer, and it has no separate rail entry or keyboard shortcut.

The Scheduled Events, Cards Against Humanity, Tambola, Casino, Economy, Leaderboard, and Stocks tabs sit beside Music. Scheduled Events manages operator-created voice playback. CAH and Tambola are operator views: they show a redacted live table and the controls the host or an administrator needs, while hands, tickets, decks, and marks stay in Discord. Casino, Economy, Leaderboard, and Stocks are member views for the signed-in Discord user. CAH and Tambola poll every five seconds only while the tab is visible, and a refresh replaces the live panel without resetting the host form, search, focus, or scroll position.

Discord ID fields that accept a channel, voice channel, role, or member also accept a name. Typing a name opens a suggestion list after a short pause. The list ranks an exact name first, then a name that starts with the text, then one that contains it. A `#channel` or `@role` fragment is understood, so `#gene` finds `#general` and `@mod` finds the matching role. Press Enter or leave the field to resolve without picking from the list: the single exact match, or the only result, is written automatically. Pressing Enter for a name does not submit the surrounding form, and submitting a form resolves any remaining name first. Choosing a suggestion writes the numeric ID into the field and shows the resolved name beside it. The field keeps the raw ID, so form submission and settings saves are unchanged. Role ID lists append the chosen role to the existing comma-separated list. Keyboard users get Up, Down, Enter, and Escape, and every resolver input accepts text on phones.

The theme is monochrome, with a light and dark palette and a toggle in the rail. The selected palette persists in local storage and defaults to the system preference. Discord guild logos appear in the server selector; guilds without an icon show their initial.

Motion only marks state. Use transform and opacity, exact transition properties, ease-out, and 90 to 190 ms. Route changes and keyboard navigation do not animate. Toasts enter and leave with transitions and faster exits. Hover motion sits behind `@media (hover: hover) and (pointer: fine)`. Reduced motion collapses every duration while keeping the end state.

## Operating notes

Feature switches, server settings, and scheduled event changes are open only to a signed-in Discord user who has the Administrator permission in the selected server. The dashboard checks that permission with the bot control API before every write and disables or hides the controls for everyone else. A failed check returns 403 `administrator_required`.

Economy, Leaderboard, Stocks, and the music join and filter controls are member actions. They read the caller from the signed-in Discord user, so they need a Discord sign-in, not the Administrator permission. A password-only session can read the music player but gets 403 `discord_account_required` from the member routes and cannot join as a member. The bot also reads the caller from `x-user-id`, so a request body cannot name another member.

Feature switches apply immediately. The dashboard shows an Undo action after each change, and a failed write reverts the switch and shows the API message inline.

The music tab shows a now-playing card with artwork when the track has it, a fallback glyph when it does not, the title, artist, a live, paused, or idle status, the connected `#channel`, and a fixed `80% volume` chip. The progress row and transport keep seek, shuffle, previous-less play or pause, skip, and loop. The four filter chips switch between Off, Bass boost, Nightcore, and Vaporwave, and the active filter is marked with `aria-pressed`. **Join my voice channel** joins the voice channel of the signed-in Discord user, so no channel is needed. The optional channel field accepts `#name`, a name, or a pasted ID and resolves it before joining; **Join channel** uses that field, and **Disconnect** leaves. **Add to queue** uses the same channel field when one is set and the member's current channel when it is empty. A password-only session can read the player and name a channel, but it cannot use **Join my voice channel** because the bot needs a Discord member to find that member's voice state. Playback volume is fixed at 80 percent and no dashboard control can change it.

### Scheduled Events

The **Scheduled Events** view lets an Administrator create, edit, enable, run, and delete voice events. Each event stores a name, a voice channel, a YouTube video link, a start time, a repeat rule, and its latest run status. The channel field resolves a name such as `#general` to the channel ID before saving.

Only a signed-in Discord user with the Administrator permission in the selected server can change events. The dashboard checks the live permission through the bot control API, and every mutation also requires a CSRF token. The bot control API checks the live guild member again before it writes. Reads require a signed-in session but do not require Administrator permission.

The service accepts YouTube video links only. It normalizes `youtube.com/watch?v=`, `youtu.be`, Shorts, Live, and embed links to a canonical watch URL. Playlist-only links, malformed video IDs, and other hosts are rejected.

Choose **One time**, **Daily**, or **Weekly**. A one-time event disables itself and clears its next-run time after it succeeds, fails, or is skipped. A daily or weekly event advances from its prior scheduled time to the first interval after the run finishes. After a restart, each overdue event runs at most once; the scheduler advances repeating events past missed intervals instead of replaying each missed day or week.

The event table shows the next run in local time, the repeat rule, enabled state, and last status. Recent runs show the event, start time, status, trigger, and error. Status uses both a label and a color. The built-in prayer phases stay read-only in this view as a separate sequence. Custom events do not replace or rewrite those phases.

The global `EVENT_SCHEDULE_ENABLED` setting controls automatic ticks. When it is off, operators can still create and edit schedules, and can run an event manually if the per-server `automation-scheduled-events` feature is on. Turning that feature off blocks manual runs and automatic scheduled events, but does not prevent operators from preparing the configuration.

Run the headless dashboard flow with `bun run --cwd apps/dashboard test:events-browser`. Install Playwright Chromium and its required host libraries first.

The bot control API exposes `GET /v1/events`, `POST /v1/events`, `PATCH /v1/events/:id`, `DELETE /v1/events/:id`, and `POST /v1/events/:id/run`. Every request needs the control bearer token and an explicit `x-guild-id`. Mutations also need the caller's `x-user-id`; the bot fetches that member from the selected guild and checks the Administrator permission. The control API returns refreshed event state after each mutation.

Server settings save one section at a time. Boolean switches save their visible state, and role ID fields accept a comma-separated list. The welcome channel, goodbye channel, voice hub, category, music channel, and role ID fields also resolve names to IDs: type `#channel-name` for a channel or `@role-name` for a role, and choosing a role appends its ID to the list. The music section no longer exposes a default volume, because playback is fixed at 80 percent; a previously stored value is kept but unused.

Audit entries show the actor's Discord display name when the bot can resolve it. Hover the name or focus it to read the Discord ID. A non-Discord actor such as `dashboard`, `system`, or `mcp` keeps its name. When the bot cannot resolve a Discord ID, the dashboard labels the actor `Discord member` and keeps the ID in the title.

## Member and game tabs

The **Cards Against Humanity** tab follows the lobby, submission, judging, reveal, and finished states. It shows the game ID, channel, host, phase, points goal, players and scores, black card, submission count, and anonymized white-card slots at judging and reveal. It does not show hands, decks, discards, submission owners, the judge order, timers, or Discord message objects. Hosts can create a lobby from a text channel ID, start it, force a reveal, advance a round, and end it. Reveal and advance also work for the current judge. Ending also works for an administrator. The judge picks the winning slot in Discord; the dashboard deliberately has no pick route. The Discord link opens the lobby or game channel.

The **Tambola** tab follows the live table: status, host, channel, player count and names, called count, last call, claims, auto-mark, call interval, and voice state. It does not show tickets or marked numbers. The host or an administrator can pause, resume, or end the game. Ending releases the call, lobby, game, and voice timers, leaves voice, unlocks music, and drops the TTS voice path. Players still join, buy tickets, mark numbers, and claim lines in Discord.

The **Casino** tab is for the signed-in member, not an operator action. It shows the member's balance and two games: coinflip spends the bet and pays 2x on a 48% win; slots pays 5x for three of a kind and 1.6x for a pair, rounded down. The maximum bet is 10,000 SC, and a bet must be a positive whole number. Spend and payout use idempotency keys derived from a client request ID. The roll is an HMAC of that ID with a server-side secret, so a retry returns the same result, charges once, and a client cannot grind request IDs to predict a win. Only your own balance is read or changed. Blackjack is not in the dashboard.

CAH and Tambola controls need a Discord sign-in, because the bot checks the acting member's host, judge, and Administrator permissions. A password-only session can read the CAH and Tambola tables but cannot use their controls. Casino needs a Discord sign-in because the balance and bets belong to a Discord user.

### Economy and Leaderboard

The **Economy** tab is self-service. It shows your balance, daily streak, total earned, total spent, and the ready state of the daily reward and work shift. **Claim daily** and **Work a shift** act on your own Discord account. A cooldown disables the button and prints the time it becomes ready again. A cooldown response from the bot carries the same time in its message. The view shows a feature notice when `economy-core` is off.

The **Leaderboard** tab lists the top 25 accounts with rank, member name, and balance. Your own row is marked, and your rank and balance appear above the table. The bot resolves names from the guild member cache and fetches missing members when it can; a member it cannot resolve appears as a Discord ID. Birthdays and other member data are not part of this response.

### Stocks

The **Stocks** tab is also self-service. It shows the exchange index and its change. The market table lists price, change from the previous history point, and a small trend line. Your portfolio shows cash, holdings value, net worth, and unrealized profit or loss. The trade form buys or sells whole shares for your own account. Each trade costs a 1% fee rounded up to at least 1 SC. A trade returns the fresh market and portfolio, so the view updates without a page reload. The submit buttons disable while a trade is in flight. The stock service is not idempotent, so the dashboard does not retry a trade automatically.

## Discord sign-in

Discord OAuth can run beside the password or replace it. Create a Discord application or reuse the bot's, open **OAuth2 > Redirects**, and add the exact public callback:

```text
https://dashboard.example.com/auth/discord/callback
```

Then set four values in `.env`:

```sh
DISCORD_CLIENT_ID=...          # already present for the bot
DISCORD_CLIENT_SECRET=...
DASHBOARD_OAUTH_REDIRECT_URI=https://dashboard.adityavikram.dev/auth/discord/callback
DASHBOARD_OWNER_IDS=123456789012345678,234567890123456789
```

All four are required together. A partial set makes the dashboard exit at startup. When `DASHBOARD_PASSWORD` is unset, they are also the only sign-in method. Only the listed Discord user IDs can sign in. The flow uses a short-lived state cookie, exchanges the code server-side, fetches the user with `identify`, and stores only the id, display name, and avatar in the signed session cookie. Access and refresh tokens are never stored.

Start the sign-in from the public HTTPS origin, not the LAN IP. The state cookie is host-only, so starting at the LAN address and returning to the public callback fails with `oauth=state`.

When `DASHBOARD_PASSWORD` is set, the password form remains available beside Discord. When it is absent, the dashboard hides the password form and `POST /api/login` returns 404 `password_disabled`, so the Discord values must be complete. The owner allowlist decides who can sign in with Discord. A password session can read the dashboard, but it cannot change features or server settings, use game controls, play the casino, or manage a birthday, because those actions need a Discord user ID. Sign in with Discord to make changes.

If the OAuth values are absent, the Discord button is hidden, `/auth/discord` returns 404, and the password is the only sign-in method.

All `/api` routes except login require a valid session. Mutations also require the `x-csrf-token` header. The music route accepts only `join`, `play`, `pause`, `resume`, `skip`, `stop`, `seek`, `loop`, `shuffle`, `clear`, `filters`, and `disconnect`, and only `join` and `play` accept a voice channel. Join and play forward the signed-in Discord user so the bot can act on that member's voice state. Volume is fixed at 80 percent, so there is no volume action. The CAH route accepts only `start`, `reveal`, `next`, and `end`. The Tambola route accepts only `pause`, `resume`, and `end`. The economy route accepts only `daily` and `work`. The stock route accepts only `buy` and `sell`. The dashboard has no generic proxy route. HTML, JavaScript, and CSS static responses carry `cache-control: no-store` so a deploy is picked up on the next load; fonts and images stay cacheable for an hour.

## Session and request security

The `siela_dashboard` cookie contains the expiry, optional Discord identity, and an HMAC-SHA256 signature. It is `HttpOnly` and `SameSite=Lax`, and expires after 12 hours. The server compares signatures, CSRF tokens, and passwords in constant time. Password login allows five attempts per IP in each five-minute window.

The server sets a restrictive content security policy, denies framing, disables MIME sniffing, and sends a no-referrer policy. Images may come from the Discord CDN and from the artwork hosts the bot stores, `i.ytimg.com`, `img.youtube.com`, and `*.sndcdn.com`. Static requests resolve inside `apps/dashboard/public`; traversal and symlink escapes are rejected. The container runs read-only, drops capabilities, and writes only to its `/tmp` tmpfs.

The browser never receives `MCP_TOKEN`. `apps/dashboard/src/control-client.ts` is the single server-side adapter for bearer-authenticated requests. It sets `x-guild-id` on every guild-scoped control request, `x-user-id` on permission, birthday, game, economy, stock, music join or play, and scheduled event mutation requests, and `x-actor` to the signed-in Discord user on writes. Dashboard route parameters, methods, configuration sections, music actions, scheduled event bodies, game actions, casino games, economy actions, stock actions, and resolve kinds are allowlisted before they reach that client.

The bot control API owns the permission check. `GET /v1/authorize` fetches the member from the selected guild and tests the Administrator flag. The dashboard treats a missing member, a non-Administrator member, and a failed check as no permission. Feature and settings writes return 403 `administrator_required`. Birthday routes read the caller from `x-user-id` and never accept a target user, so one member cannot read or change another member's birthday. CAH and Tambola controls also read the caller from `x-user-id`, then check the live game's host, judge, and Administrator rules. Casino, economy, stock, and music routes read the caller from `x-user-id`, so a request body cannot name another member. Game state projections are redacted in the bot service before they reach the dashboard; the control API never sends hands, decks, tickets, marks, judge order, timers, or Discord message objects.

`GET /v1/resolve` reads the selected guild only. It searches cached guild channels, roles, and members, then asks Discord for members when the cache misses. It returns an ID, name, kind, display label, and an optional description that marks bots and the everyone role. It never returns message content or anything from another guild.

## Network boundary and guild scope

Compose attaches the dashboard to the `edge` network for browser traffic and to the internal `control` network for bot requests. Only the dashboard's port is published. Keep `bot-control:3001` on the internal control network and do not publish it to the host or the internet.

The operator selects a server in the header. The dashboard stores that selection in `localStorage` and reflects it in the hash route. Each server-scoped request sends that server's ID in `x-guild-id`; the control API then scopes reads and writes to that guild. The server list and status endpoints are not guild-scoped.

The control API must expose the routes in the dashboard build contract. In particular, the guild, feature, and game routes are control API work. Until they are present in a deployment, the dashboard reports the control API's error inline. A missing or invalid bearer token has a distinct message, and a network failure reports that the control API is unreachable.
